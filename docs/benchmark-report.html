🎯 核心发现（含用户体感）

  • sequence 三种存储模式性能几乎一致（~370 ops/s 单线程）
    → 用户体感：生成一个 ID 的延迟恒定 2.4ms，无论用 MySQL/Redis 还是单机模式，API 响应速度无差别。不需要为了性能选存储——按运维偏好选即可。
    → 生产预期（2C4G ECS）：约 60~90 ops/s，单次延迟 ~12ms。每天生成 500 万+ ID 毫无压力。
  • lock Redis 比 MySQL 快 2.5~6 倍（Redis P50=5.9ms vs MySQL P50=15.2ms）
    → 用户体感：定时任务加锁/释放增加 6~15ms——远低于人类感知阈值（100ms），两种模式用户均无感。
    → 什么场景选什么：并发抢锁频率 <100次/秒 → MySQL 够用（不引入新组件）；>100次/秒或已有 Redis → 选 Redis。
    → 生产预期（2C4G ECS + RDS MySQL）：MySQL 锁约 15~20 ops/s（跨机网络 I/O 放大），Redis 锁（同 VPC ECS+Redis）约 80~120 ops/s。定时任务场景（每秒最多几个锁操作）完全够用。
  • async 内存模式比 MySQL 快 1.6~2.7 倍（standalone 369 vs mysql 135 ops/s 单线程）
    → 用户体感：提交一个异步任务后 2~7ms 即返回，任务执行在后台异步完成。
    → 什么场景选什么：允许重启丢失（工具类/日志类）→ standalone（零 DB 依赖）；可靠性要求（订单/通知）→ mysql（崩溃后悬挂回收自动恢复）。
    → 生产预期（2C4G ECS + RDS）：MySQL 模式约 20~35 ops/s 提交。1000 个用户的"报告生成"请求在 30 秒内全部入队。
  • 进程内 vs RPC 层：组件自身开销可忽略（ID 生成进程内 78ns → RPC 2.4ms，30,000×）
    → 用户体感：三组件的逻辑耗时是纳秒~微秒级——生产瓶颈永远在 HTTP/JSON/数据库网络，不在组件本身。选哪个组件、选哪种模式，对 API 响应时间的影响都在 10ms 以内。

💥 故障注入 — 打崩后的真实形态（单机 + 双实例，2026-10-31）

核心结论：这套系统的「崩」不是报错崩溃，而是静默挂起——最阴险的失效形态。不配超时参数时 DB 故障无任何拒绝信号（无 5xx、无连接拒绝），health 挂死会引发编排连环重启。

MySQL pause 40s（挂起）lock 600 请求 64 超时、吞吐 110→2 ops/s；恢复瞬间 40s 慢 SQL 洪峰✅ 完全自愈
MySQL stop（断连）请求无限挂起（连 5xx 都没有）——docker-proxy 接受 TCP 不转发 + 驱动默认 connectTimeout=0✅ 重启秒级恢复
